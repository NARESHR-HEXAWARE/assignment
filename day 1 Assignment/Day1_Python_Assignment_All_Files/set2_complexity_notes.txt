SET 2 — RETAIL BANKING TRANSACTION REVIEW: COMPLEXITY

Task | Best time | Average time | Worst time | Extra space
Linear search | O(1) | O(n) | O(n) | O(1)
Binary search (sorted IDs) | O(1) | O(log n) | O(log n) | O(1)
Insertion sort | O(n) | O(n^2) | O(n^2) | O(1) plus copied input
Merge sort | O(n log n) | O(n log n) | O(n log n) | O(n)
Duplicate detection after sorting | O(n log n) | O(n log n) | O(n log n) | O(n)
Queue and stack operations | O(1) amortized | O(1) | O(1) amortized | O(n)
Divide/conquer min-max | O(n) | O(n) | O(n) | O(n) with slices
Brute force scan | O(n) | O(n) | O(n) | O(1)

SEARCH: 100,000 IDs, 1,000 sample IDs, comparison counts reported.
STATEMENTS: stable insertion/merge sort retain original relative order of
transactions that have identical posting timestamps. Stable ordering makes
statement display reproducible; a secondary transaction ID tie-breaker can
also be used when a specific chronological tie order is required.
DUPLICATES: hash dictionary stores last seen timestamp for each
(account, amount, merchant) after chronological sort. Time differences
within 60 seconds are flagged. A production system must define how to handle
repeated groups and out-of-order streams, and use decimal monetary amounts.
QUEUE and STACK: handwritten array-backed FIFO and LIFO.
MIN/MAX: divide-and-conquer is O(n) but recursive slicing and call overhead
can make it slower than a simple Python scan; the measured timings show this.
